# Interview questions: multisig-wallet

## Q1. Why make a protocol's admin a multisig instead of one key? What does it protect against, and what doesn't it?

Answer: With one admin key, anyone who steals, phishes or leaks that key gets the protocol's full power immediately. If the key is lost, the power is gone for good. Making a 2-of-3 multisig the admin, as `FeeController` does here, separates holding a key from holding the power. One compromised key can submit and approve, but it can't reach the threshold, as `test_OneStolenKeyCannotChangeFee` shows. It also covers a lost key, because the other two owners can rotate it out with `replaceOwner`. It doesn't protect against two keys being compromised at once, which is more likely than it sounds if owners share a device, a password manager or a signing interface. It doesn't help when honest signers approve a malicious payload they didn't read ("blind signing"). The 2025 Bybit theft worked this way, through a tampered signing UI. And it can't fix bugs in the wallet or in the contract it administers.

## Q2. My first design stored an approval count on each transaction. Rotating an owner exposed a bug. Walk me through it and the fix. What general lesson does it teach about cached state?

Answer: Each transaction had an `approvals` counter that `approve` increased and `revoke` decreased, alongside the `hasApproved` mapping. In `test_StaleApprovalDoesNotCount`, a stolen key belonging to Carol submits a 5 ether drain and approves it, so the counter is 1. Alice and Bob then rotate Carol out, but `replaceOwner` never touches the counter, so it stays at 1. When Alice approves the drain by mistake, the counter reaches 2 even though only one current owner approved, and `execute` would have paid Mallory. The fix wasn't to patch `replaceOwner`. I deleted the counter and made `approvalCount` loop over the three current owners, checking `hasApproved`. The general lesson is that a cached value has to be updated on every path that changes what it's derived from, and adding a new path (here, owner rotation) is when that gets forgotten. When recomputing is cheap and bounded, as with three owners, deriving the value from a single source of truth removes this whole class of bug.

## Q3. `execute` sets `executed` to true before the call. What does that prevent, and why can a failed transaction still be retried if the flag was already set?

Answer: It prevents reentrancy. The external call hands control to the recipient, and a malicious recipient can call `execute` again before the first call finishes. Because the flag is already `true`, that nested call hits `notExecuted` and reverts with `AlreadyExecuted`, so the transaction pays exactly once. This is checks-effects-interactions: validate, update your own state, and only then interact with other contracts. A failed transaction stays retryable because EVM transactions are atomic. When the call returns `false`, `execute` reverts with `ExecutionFailed`, and a revert undoes every state change in that call frame, including `executed = true` and the `Executed` event. So the flag is only ever permanently set together with a successful call. `test_FailedCallCanBeRetried` checks exactly this: it fails for lack of funds, the wallet is topped up, and the retry pays.

## Q4. Replay and reentrancy both pay someone twice. How are they different, and why did my replay test still pass when I moved the flag after the call?

Answer: A replay is a second, separate execution of a transaction that already completed. It happens later, in a new call, after the first one has fully finished and stored its state. Reentrancy is a nested execution that happens during the first one, while its external call is still running and before it has finished updating its state. `test_RevertWhen_ExecutingTwice` is a replay test: it calls `execute`, waits for it to return, and calls again. When I moved `executed = true` to after the call, the flag was still set by the time the first `execute` returned, so the second call reverted and the test passed. Only `test_ReentrantExecutePaysOnce` failed, because its attacker re-entered from `receive()` while the flag was still `false`, and drained 5 ether instead of 1. The takeaway is that "can't execute twice" and "can't re-enter" need separate tests. A reentrancy bug can pass every test that only calls the contract one transaction at a time.

## Q5. How does this wallet differ from Safe? Cover off-chain EIP-712 signatures, nonces, modules, and why production teams usually add a timelock.

Answer: Here every approval is its own on-chain transaction that pays gas. In Safe, owners sign the transaction off-chain as EIP-712 typed data, and one `execTransaction` call checks all the signatures together. The EIP-712 "domain" includes the chain ID and the Safe's address, so a signature can't be reused on another chain or another Safe. Because signatures live off-chain, Safe needs a nonce. Each signature covers the current nonce, which increases with every execution, so a signed transaction is valid exactly once and transactions run in order. This wallet instead uses a `txId` and an `executed` flag. Safe also supports any M-of-N setup with owner and threshold management, and modules: enabled contracts that can execute without signatures, used for things like spending allowances or recovery. Modules are powerful and a common risk if misconfigured. Production teams add a timelock because a multisig decides who can act, not when. A delay between approval and execution gives users and monitoring systems time to spot a malicious transaction and react, or withdraw their funds, even if enough keys are compromised.
